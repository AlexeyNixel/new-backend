# Исправление `/posts/migrate` (миграция новостей не работала)

## Задача

После починки `/files/migrate` пользователь сообщил, что не работает и миграция новостей
(`GET /posts/migrate` → `PostsService.migratePosts`).

## Диагностика (systematic-debugging)

### Проводка

В прошлой сессии контроллер уже поправили — `migrate()` вызывает `migratePosts()` (не `migratePostOnRubric()`).
Значит, проблема в самом методе.

### Сбор доказательств (прямые запросы к обеим БД)

**Исходная `db_noub_new.Entry`:** 4799 строк.
**Целевая `nomb_dev.posts`:** 4707 строк, **4705 из 4799 исходных уже перенесены** (совпадение по `id`).
Реально не хватает **94 новостей**.

Проверка этих 94 недостающих строк — данные чистые:
- `slug`: нет NULL/пустых, нет превышения длины, нет дублей внутри пачки, нет конфликтов с уже существующими;
- `title`: нет NULL, длины в норме;
- `departmentId`: все 94 ссылаются на существующие отделы;
- `fileId`: все 94 ссылаются на существующие файлы.

То есть все 94 записи мигрировались бы без ошибок, **если бы цикл до них дошёл**.

## Корневая причина

`PostsService.migratePosts()` — не идемпотентный, как и был `FilesService.migrate()`:

```ts
for (const post of oldPost) {
  try {
    // ... prismaService.post.create({ data: { id: post.id, ... } })  // без проверки существования
  } catch (e) {
    throw new Error(e);   // ← любая ошибка обрывает весь цикл
  }
}
```

Проверки «пост уже существует» нет. Поскольку 4705 из 4799 записей уже в целевой таблице,
на первой же существующей строке `post.create()` падает с нарушением уникального ограничения
(PK `id` или уникальный `slug`), блок `catch` делает `throw new Error(e)` → весь цикл прерывается →
NestJS отвечает 500, ни одна из 94 новых новостей не создаётся. Снаружи — «миграция не работает».

### Дополнительный (латентный) баг

Запасной `previewFileId: '123ec8e5-650c-47b6-a898-203b40987a29'` (для записей без своего файла)
**не существует** в целевой таблице `files`. Любая запись без валидного `fileId` упала бы на нарушении
внешнего ключа. В аналоге `MigrationService.migratePosts()` используется другой заглушечный id
(`aa8c3d9e-f7de-44cc-8391-b6e7f8782ce3`), который в `files` есть.

## Исправление

`src/posts/posts.service.ts`, метод `migratePosts()`:

- перед `create()` — проверка `findUnique({ where: { id } })`, существующие пропускаются;
- каждая итерация в `try/catch` с накоплением ошибок вместо `throw` (одна битая запись не рушит миграцию);
- рабочий запасной `previewFileId` вынесен в константу `DEFAULT_PREVIEW_FILE_ID`
  (`aa8c3d9e-...`, реально существует в `files`);
- метод возвращает сводку `{ total, migrated, skipped, failed, errors }` (раньше возвращал
  `'Постов пропущенно 0'` — константу, которая никогда не менялась);
- убран мёртвый код (`errorsCount`, `@ts-ignore`).

## Проверка

- `npx tsc --noEmit` — без ошибок.
- `npm run build` — успешно.
- `npx eslint src/posts/posts.service.ts` — 8 ошибок (все в нетронутом коде: `migratePostOnRubric`,
  `findAll`, `update`); правка убрала 1 ошибку и 1 предупреждение, новых не внесла.
- Прогон новой логики на боевых БД внутри Prisma-транзакции с принудительным откатом
  (ничего не записано): `{ total: 4799, migrated: 94, skipped: 4705, failed: 0, errors: [] }`.

## Осталось сделать

- Запустить `GET /posts/migrate` (с JWT) — перенесёт 94 новости. В рамках диагностики данные не писались.
- После постов имеет смысл прогнать `GET /posts/migrate/tag` (связи новость↔рубрика).
- Устранить дублирование логики миграции: `PostsService`/`FilesService` vs `MigrationService`
  (см. память проекта `migration-logic-duplicated`).
