# Исправление эндпоинта `/files/migrate` (миграция изображений не работала)

## Задача

Пользователь сообщил, что не работает миграция изображений через `GET /files/migrate`
(`FilesController.migrate` → `FilesService.migrate`).

## Диагностика (systematic-debugging)

### Проверка проводки

Эндпоинт подключён верно: `FilesController.migrate()` вызывает `filesService.migrate()`
(в отличие от бага `/posts/migrate`, где вызывался не тот метод). `@InjectDataSource('sourceDB')`
работает — `TypeOrmModule.forRootAsync({ name: 'sourceDB' })` регистрируется глобально
(`src/app.module.ts:42`), тот же паттерн используется в рабочих модулях (posts, tags, book и др.).

### Сбор доказательств (прямые запросы к обеим БД)

**Исходная БД (`db_noub_new`, таблица `File`):** данные чистые —
15 878 строк, дублей `id`/`hash` нет, NULL в обязательных колонках нет, длины в пределах лимитов,
значения `type` (`IMAGE`, `DOCUMENT`, `EXHIBITION`) все входят в целевой enum `FileType`.

**Целевая БД (`nomb_dev`, таблица `files`):** уже содержит **15 388 строк**.
Пересечение с исходной БД: **15 369 строк из 15 878 уже перенесены** (совпадают и по `id`, и по `hash`).
Реально не хватает только **509 файлов** (490 IMAGE, 14 DOCUMENT, 5 EXHIBITION) — все без конфликтов.

Файлы уже были перенесены ранее через `MigrationService.migrateFiles()` (`src/migration/migration.service.ts:78`) —
параллельную реализацию той же логики, в которой **есть** проверка на дубликаты.

## Корневая причина

`FilesService.migrate()` был не идемпотентным: для каждой строки исходной БД вызывался
`prisma.file.create()` **без проверки существования и без `try/catch`**:

```ts
for (const file of oldFiles) {
  await this.prismaService.file.create({ data: { id: file.id, /* ... */ } });
}
```

Поскольку 15 369 из 15 878 строк уже есть в целевой таблице, на первой же существующей записи
`create()` падал с ошибкой уникального ограничения Prisma (P2002, по PK `id` / уникальному `hash`).
Исключение вылетало из цикла и из метода → NestJS отвечал 500, метод не возвращал ничего,
ни один из 509 недостающих файлов не создавался. Снаружи это выглядело как «миграция не работает».

Это тот же класс бага, что и в отчёте по `/posts/migrate`: дублирование логики миграции,
и копия в доменном модуле не имеет защиты от дублей, которая есть в `MigrationService`.

## Исправление

`src/files/files.service.ts`, метод `migrate()`:

- добавлена сортировка `ORDER BY createdAt` (детерминированный порядок);
- перед `create()` — проверка `findUnique({ where: { id } })`, существующие записи пропускаются;
- каждая итерация обёрнута в `try/catch`, ошибки собираются, а не прерывают миграцию;
- метод возвращает сводку: `{ total, migrated, skipped, failed, errors }`;
- удалена отладочная строка `console.log(oldFiles)`;
- строкам исходной БД задан явный тип (убирает `no-unsafe-*`).

## Проверка

- `npx tsc --noEmit` — без ошибок.
- `npm run build` (`nest build`) — успешно.
- `npx eslint src/files/files.service.ts` — 0 ошибок (1 предупреждение было и до правки, в `uploadExhibition`).
- Прогон новой логики на боевых БД внутри Prisma-транзакции с принудительным откатом
  (ничего не записано): `{ total: 15878, migrated: 509, skipped: 15369, failed: 0, errors: [] }`.

## Осталось сделать

- **Запустить саму миграцию** — вызвать `GET /files/migrate` (с JWT). Ожидаемо: перенесёт 509 файлов.
  В рамках диагностики данные не записывались.
- Рассмотреть устранение дублирования: логика миграции файлов/постов есть и в доменных модулях
  (`FilesService`, `PostsService`), и в `MigrationService`. Стоит оставить один источник правды.
