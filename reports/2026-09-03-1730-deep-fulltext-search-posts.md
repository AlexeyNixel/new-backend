# Глубокий полнотекстовый поиск по новостям

## Задача

Сделать поиск по новостям (`GET /posts?search=`) «глубже» — искать по всему тексту
статьи, а не только по совпадению подстроки, и ранжировать по релевантности.

## Что было не так

`PostsService.findAll` строил условие поиска так:

```ts
OR: [{ title: { contains: search }, content: { contains: search } }]
```

Один объект внутри `OR` — это **AND**: слово должно было встретиться **и** в заголовке,
**и** в теле одновременно. Плюс:

- `description` в поиске не участвовал;
- многословный запрос искался как одна подстрока;
- тело — HTML, `LIKE` цеплял текст внутри тегов (`src="...jpg"`, `style=...`);
- ранжирования по релевантности не было;
- новости с `content IS NULL` вообще не попадали в выдачу даже при пустом поиске
  (`NULL LIKE '%%'` → `NULL`).

Замер: по запросу «библиотека» отдавалось **315** новостей вместо **~2350**;
44 новости со словом только в заголовке терялись полностью.

## Что сделано

### 1. Схема БД + миграция `20260903092556_posts_fulltext_search`

- Колонка `posts.contentText` — тело новости без HTML. Это **генерируемая STORED-колонка**:
  MySQL/MariaDB пересчитывает её сама на каждый `INSERT`/`UPDATE` строки `posts`
  (из `content`, через вложенные `REGEXP_REPLACE`: вырезаются `<script>`/`<style>`
  с телом, остальные теги, HTML-сущности, схлопываются пробелы). Приложение колонку
  не пишет — её нет в `data` при `create`/`update`.
- `FULLTEXT`-индекс `posts_title_description_contentText_idx` по `(title, description, contentText)`.
- В `schema.prisma`: поле `contentText String? @db.LongText` (обычное, с комментарием) +
  `@@fulltext([title, description, contentText])`. Prisma не моделирует генерируемые
  колонки, поэтому DDL в `migration.sql` дописан руками (как baseline map_points);
  `prisma migrate diff` подтвердил — новых расхождений схемы нет, Prisma видит колонку
  как обычный nullable LongText.
- Бэкофилл не нужен: на `ADD COLUMN` MariaDB посчитала `contentText` для всех 4801 строк.

### 2. Поиск в `PostsService`

- Новый утиль `src/posts/utils/fulltext-query.ts` — `toBooleanFulltextQuery(search)`:
  разбивает запрос на слова, чистит спецсимволы boolean-режима, отбрасывает слова
  короче 3 символов (`innodb_ft_min_token_size`), строит `+слово1* +слово2*`
  (все слова обязательны, `*` — префиксный матч словоформ). Возвращает `null`,
  если осмысленных слов не осталось. Покрыт unit-тестами (`fulltext-query.spec.ts`, 8 шт).
- `findAll`: если `toBooleanFulltextQuery` вернул строку — ветка поиска:
  - приватный `searchPostIds()` — `$queryRawUnsafe` с
    `MATCH(title, description, contentText) AGAINST(? IN BOOLEAN MODE)`,
    те же фильтры (удалённость, отдел, даты, теги) в том же WHERE,
    `ORDER BY publishedAt DESC, id` (сначала новые новости — как в обычном списке;
    `id` — для стабильной пагинации), `LIMIT/OFFSET`; отдельный `COUNT(*)`;
  - затем `prisma.post.findMany({ where: { id: { in: ids } }, include })` и пересортировка
    по порядку релевантности — так сохраняются `include` (теги/превью/отдел) и формат
    `responseService.paginated`.
- Пустой/короткий запрос — прежний путь (`findMany` + `count`), но **без битого `OR`**:
  теперь пустой поиск честно отдаёт все новости, включая те, где `content IS NULL`.

### 3. Чего намеренно не делали (YAGNI)

Морфология/стемминг русского, терпимость к опечаткам, подсветка совпадений,
weighted-ранжирование «заголовок важнее» (лёгкое расширение — отдельный `FULLTEXT(title)`).
Внешний поисковый движок (Meilisearch/Typesense) — избыточно для 4801 записи.

## Проверка

- `npx tsc --noEmit`, `npm run build` — без ошибок.
- `npx jest` — 8/8 (`fulltext-query.spec.ts`). В проекте это первые тесты.
- `npx eslint` по изменённым файлам — новый код чистый; в `posts.service.ts` осталось
  6 pre-existing ошибок `no-unsafe-*` в нетронутых методах (было 9 + 1 warning).
- Ручная проверка на боевой БД (4801 новость) через реальный `$queryRawUnsafe`:
  одно слово, два слова (оба обязательны), словоформы по падежам, фраза из тела статьи,
  фильтры по отделу и дате, пагинация, мусорный ввод — всё корректно;
  relevance приходит как `number`, count как `bigint` (обрабатывается);
  «библиотека»: 315 → 2256 (с учётом `isDeleted = false`); новости со словом только
  в заголовке теперь находятся (3/3).

## Осталось / на заметку

- **`prisma generate` не удалось выполнить** — `generated/prisma/query_engine-windows.dll.node`
  залочен запущенным `npm run start:dev`. На фичу это не влияет (клиент к `contentText`
  типизированно не обращается, `$queryRawUnsafe` есть в текущем клиенте). Нужно один раз
  выполнить `npx prisma generate` после остановки dev-сервера (либо оно отработает на
  `npm ci` / деплое через `postinstall`).
- Ветка поиска сортирует строго по `publishedAt DESC` (сначала новые), релевантность
  на порядок не влияет. Произвольный `sortBy`/`sortOrder` в поиске не применяется —
  если понадобится, добавить несложно.
- Пограничный pre-existing баг: `isDeleted` из query приходит строкой без трансформации,
  `?isDeleted=false` (строка) → truthy. Поведение сохранено как в старом коде, не чинил.
